Design patterns

Where design patterns fit in the trading platform

The platform benefits from patterns that isolate strategy rules, broker integrations, order creation and state transitions. The goal is not to use patterns for their own sake; each one reduces coupling in a specific part of the workflow.

PatternWhere it fitsHow it helpsExample responsibility
Strategy PatternStrategy EngineAllows different trading algorithms to share the same execution contract without changing the orchestration flow.Different option/entry/exit strategies implement a common strategy interface.
Factory PatternOrder EngineCentralizes creation of order requests so the rest of the system does not depend on concrete order types.Create BUY/SELL, market/limit or instrument-specific order objects from a normalized command.
Adapter PatternBroker integrationHides broker-specific REST/WebSocket formats behind application-level interfaces.Convert broker payloads into internal market-data/order models.
Observer / Event-driven approachMarket-data processingSeparates the incoming market-data event from consumers that react to it.A price/tick event can be consumed by strategy, monitoring and persistence components.
State PatternOrder / position lifecycleMakes lifecycle transitions explicit instead of scattering status checks throughout the code.NEW → SENT → OPEN/PARTIALLY_FILLED → FILLED/CANCELLED/REJECTED.
Facade PatternTrading orchestrationProvides a simple entry point over strategy, risk, position and order operations.A trading workflow coordinates multiple subsystems without exposing their internal details to the caller.
💡 Key idea: Strategy Pattern controls which decision algorithm is used; Factory controls how order objects are created; Adapter controls how external broker APIs are translated; State controls how orders/positions move through their lifecycle.
Detailed decision pipeline

How a market event becomes a controlled order

Tick received→Deserialize Protobuf→Normalize market data→Strategy Pattern→Risk checks→Position check→Order Factory→Broker Adapter

Why normalize data?

The strategy should not know the broker's raw message structure. A normalized internal model keeps strategy logic independent from transport and vendor-specific payloads.

Why separate risk from strategy?

A strategy can produce a signal, but risk management decides whether that signal is permitted. This prevents business strategy code from becoming responsible for global exposure and safety rules.

The lifecycle is useful for handling asynchronous broker responses, retries, reconciliation and operational debugging. A status change should be treated as a state transition rather than just a random field update.

Failure handling

Important real-time failure cases

WebSocket disconnect

Detect connection state and recover the market-data channel safely.

Order rejection

Separate transport failure from broker-side rejection and update state accordingly.

Duplicate execution

Use identifiers and state checks to prevent accidental repeated actions.
